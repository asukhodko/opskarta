# opskarta v3 по сравнению с v2

Этот документ объясняет практическую разницу между opskarta v2 и v3: зачем появилась v3, что изменилось и когда переход действительно полезен. Механические шаги перехода описаны в [MIGRATION.md](MIGRATION.md).

## Коротко

v3 — это **v2 плюс официальный operational/executive layer**.

Главный скачок v2 был в разделении структуры работ и календарного планирования:

- `nodes` описывают работы и зависимости;
- `schedule` добавляет даты только там, где нужен календарный слой;
- `views` строят разные срезы из одного источника.

v3 сохраняет эту основу и добавляет слой, который нужен, когда план становится живым артефактом программы: executive-карты, статусные секции, Gantt-окна, операционные фильтры и штатное обновление Markdown.

## Что осталось тем же

| Область | Поведение v2, сохранённое в v3 |
|---------|--------------------------------|
| Модель работ | Работы по-прежнему задаются в `nodes`. |
| Schedule overlay | Даты по-прежнему живут в `schedule.nodes`, а не в `nodes`. |
| Опциональный schedule | План без `schedule` по-прежнему валиден. |
| Views | Views выбирают и рендерят работы; они не считают расписание. |
| Execution overlay | `execution.nodes` по-прежнему хранит фактический прогресс. |
| Многофайловые планы | Фрагменты плана по-прежнему сливаются в один Merged Plan. |

Поэтому большинство валидных v2-планов можно перевести в v3 заменой `version: 2` на `version: 3` и запуском v3-валидации.

## Что добавляет v3

| Область | v2 | v3 | Практическая польза |
|---------|----|----|---------------------|
| Управленческий слой | Custom-данные в `x` или внешние документы. | Встроенный профиль `x.exec`. | Статус программы становится структурированным и рендеримым. |
| Executive map | Нет стандартного формата. | `render executive` строит Mermaid flowchart из `x.exec.views`. | Один источник даёт карту для синка или руководительского среза. |
| Status report | Нет стандартного формата. | `render executive-report` строит `status`, `tracks`, `signals`. | Ручные сводки заменяются переиспользуемыми Markdown-секциями. |
| Gantt-фокус | Views фильтруют, но длинный timeline остаётся шумным. | `window_start` / `window_finish` обрезают Gantt-вывод. | Большой план можно показать только в нужном календарном окне. |
| Поддержка lanes | В lanes перечисляются конкретные nodes. | `expand_descendants: leaves` раскрывает крупные lane nodes до leaf-задач. | View остаётся коротким, а вывод показывает конкретные работы. |
| Операционные фильтры | Core-фильтры покрывают kind/status/schedule/parent. | `where.x_ops_attention_class` фильтрует по `node.x.ops.attention_class`. | Можно напрямую выбрать держателей даты, хвосты и другие операционные классы. |
| Markdown workflow | Внешние скрипты или ручной copy/paste. | `update-markdown` стал штатной командой. | Живые документы обновляют generated blocks по embedded commands. |
| Язык отчёта | Не применимо. | `executive-report --lang ru|en`. | Встроенные подписи и формат дат подходят для русских и английских документов. |

## Почему это важно

v2 отлично описывает чистую plan-as-code модель. Она отвечает:

- что является работой;
- от чего она зависит;
- какие части запланированы;
- как вывести это в tree/list/deps/Gantt.

v3 отвечает на следующий слой операционных вопросов:

- какие блоки важны к ближайшему синку;
- какая обещанная дата и текущий прогноз;
- какая ближайшая контрольная точка;
- какой трек yellow/red и почему;
- какие задачи держат дату;
- какой срез Gantt нужно показывать людям сейчас;
- как держать generated diagrams и status sections свежими внутри Markdown-документов.

Изменение не сводится к новым полям. План превращается из источника планирования в повторяемую поверхность статуса и координации.

## Когда v3 действительно полезна

Используйте v3, если верно хотя бы одно:

- план используется на регулярных синках;
- есть статусные обновления для руководителей или стейкхолдеров;
- полный Gantt слишком широкий для повседневных решений;
- рядом с планом уже ведутся ручные статусные сводки;
- нужна короткая карта ворот, владельцев, health и blockers;
- generated diagrams или report sections живут внутри Markdown-документов;
- операционные метки вроде `date_holder` или `tail` полезны для фильтрации.

В этих случаях v3 уменьшает дублирование: один структурированный источник питает validation, Gantt windows, executive maps и status text.

## Когда v2 всё ещё достаточно

Оставайтесь на v2, если план используется только для простых plan-as-code сценариев:

- tree/list/deps renders;
- обычный Gantt view;
- разделение backlog и schedule;
- без executive map;
- без generated status report;
- без living Markdown refresh workflow.

v3 не нужно воспринимать как принудительную замену v2. Она тяжелее, потому что покрывает более широкий операционный слой.

## Стоимость миграции

Для обычных v2-планов переход намеренно маленький:

1. Замените `version: 2` на `version: 3`.
2. Запустите:

```bash
python -m specs.v3.tools.cli validate *.plan.yaml
```

3. Оставьте существующие v2-style `nodes`, `schedule`, `execution` и `views`, если они проходят validation.
4. Добавляйте возможности v3 только там, где они дают пользу.

Новые поля v3 опциональны. Плану не нужны `x.exec`, Gantt windows, lane expansion или Markdown refresh, чтобы быть валидным v3.

## Концептуальное резюме

| Версия | Главная ценность |
|--------|------------------|
| v2 | Чистое разделение структуры работ, расписания, views и execution. |
| v3 | Основа v2 плюс структурированная operational reporting и executive coordination. |

Если v2 — это plan as code, то v3 — это plan as a living operational map.
